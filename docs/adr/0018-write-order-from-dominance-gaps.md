# The order of writes follows Crossing flows, not Tighten and Loosen phases

Status: superseded on 2026-11-12 by [ADR 0023](0023-writes-are-ordered-only-by-crossing-flows-with-a-settle-time.md), [ADR 0024](0024-asg-membership-is-written-as-atoms-in-member-steps.md) and [ADR 0025](0025-the-write-order-spans-environments.md) ([Review: Grill review of the complete design package](https://github.com/mfgAkilae/nsgfw/issues/23)). Accepted on 2026-11-10 ([Prototype: Translation engine worked examples](https://github.com/mfgAkilae/nsgfw/issues/22)), when it superseded [ADR 0009](0009-tighten-then-loosen-deployments.md) and amended [ADR 0010](0010-terraform-mode-data-contract-and-azure-observation.md) and [ADR 0011](0011-import-preserves-behaviour.md). Amended between 2026-11-10 and 2026-11-12 by [Task: Translation engine design doc with worked examples](https://github.com/mfgAkilae/nsgfw/issues/31), [Grilling: Write order under data-plane lag and split ASG membership writes](https://github.com/mfgAkilae/nsgfw/issues/32), [Grilling: ASG membership of private endpoints and multi-IP network interfaces](https://github.com/mfgAkilae/nsgfw/issues/39), [Grilling: Crossing flows between Environments](https://github.com/mfgAkilae/nsgfw/issues/40) and [Grilling: ASG membership on IPv6 IP configurations](https://github.com/mfgAkilae/nsgfw/issues/42). The body below is kept as history and no longer states the current decision.

[ADR 0009](0009-tighten-then-loosen-deployments.md) wrote every Deployment in a Tighten phase and a Loosen phase, with interim contents and holds, because a one-sided deny Rule could move between the source and the destination side. [ADR 0016](0016-destination-enforced-egress-and-deny-rules-on-both-sides.md) puts deny Rules on both sides. The engine prototype checked whether the order of writes still matters (prototype on the throwaway branch [`prototype/translation-engine-order-check`](https://github.com/mfgAkilae/nsgfw/tree/prototype/translation-engine-order-check/prototypes/translation-engine-order-check), result in the ticket).

**The argument.** A flow between two Zones passes the source Zone's outbound and the destination Zone's inbound NSG rules, and a Deployment replaces each Managed NSG as a whole. While a Deployment runs, each of the two NSGs holds its old or its new content. A state can allow a flow that both the Deployed state and the target deny in exactly one way: one NSG denied the flow before and allows it now, the other allowed it before and denies it now, and the one that opens is written first. A flow with one Zone endpoint passes one Managed NSG, so no order can affect it.

**What the check found.** With the placement of ADR 0016, both NSGs usually agree on a flow, so nothing crosses. Over random Change sets with every mix of old and new NSG contents per Zone, no state opened traffic for Zones, CIDRs, hosts, any, ASG objects with fixed members, both Egress postures, posture changes, IPv6 Zones outside the Internal address space, outbound Inherited defaults and three Versions in flight. Flows cross in five cases, each with a worked example: a Rule with a service tag on one side (it lands on one side only), the Inherited default "inbound from `VirtualNetwork`" with a strict source, a removed Zone (its Retired NSG denies outbound), a legacy NSG before onboarding, and ASG membership, which is a write to a network interface and not part of any NSG. As a control, ADR 0009's own deny-flip example opens traffic under ADR 0004's placement and stays closed under ADR 0016.

We decided:

- **Writes have no phases.** A Deployment writes in dependency order (a new NSG or Managed ASG before a reference to it, an association after its NSG) and otherwise in any order, in parallel where the limits allow.
- **Crossing flows add edges.** A **Crossing flow** is a flow between two Zones that one of the two Managed NSGs denies in the Deployed state and allows in the target, while the other allows it in the Deployed state and denies it in the target. The NSG that closes the flow is written before the NSG that opens it. Nothing else orders NSG writes.
- **A service tag is evaluated both ways.** The engine cannot read what `VirtualNetwork` contains for an NSG, and the Inherited defaults and legacy NSGs use that tag. For each flow and each of the two NSGs, the engine therefore evaluates both cases, the address inside the tag and outside it, and takes the edges of all cases together. It assumes only what Microsoft documents: the address spaces of the NSG's own VNet and of directly peered VNets are inside `VirtualNetwork` and outside `Internet`, and `AzureLoadBalancer` translates to the virtual IP of the host, 168.63.129.16, and includes only probe traffic, so no address of a Zone is inside it ([service tags overview](https://learn.microsoft.com/en-us/azure/virtual-network/service-tags-overview), page date 2026-09-16, retrieved 2026-11-09 for [Research: NSG and ASG rule semantics and limits](https://github.com/mfgAkilae/nsgfw/issues/2)). Every other tag, the Azure service tags included, is evaluated both ways.
- **ASG membership is written in three steps, as single joins and leaves.** A membership atom is one network interface joining or leaving one Managed ASG. Its write sets the ASG on every IPv4 IP configuration of the interface at once, because Azure rejects a network interface whose IPv4 IP configurations reference different ASGs ([Task: Empirical check of subnet NSG swaps and private endpoint ASG writes](https://github.com/mfgAkilae/nsgfw/issues/33)). Azure may still apply the IP configurations one by one on the data plane, but a flow touches one IP of the interface, so per flow the atom is applied or not, and the combination test stays exact. IPv6 IP configurations are never part of an atom: the member's IPv6 addresses reach NSGs through the IP fallback, so their joins and leaves are NSG writes. An IPv6 leave kept its membership in the effective security rules until the IPv4 IP configuration left too ([Task: Empirical check of ASGs on dual-stack network interfaces](https://github.com/mfgAkilae/nsgfw/issues/41), T10), so a member step could not rely on it. Private endpoints are no atoms: a new or removed private endpoint member changes NSG content only. Azure may apply the atoms of a step in any combination, inside one write and across parallel writes: one network interface write that moved an IP configuration from one ASG to another passed through "in both" or "in neither" in 14 of 60 swaps (T5). The engine puts each atom into a step by its own effect. An atom that, applied alone to the Deployed members, only closes traffic under the Deployed NSG contents goes into the first step. Every other atom goes into the last step. Between them come the NSG writes that the steps can affect, with their edges computed against the members as they are after the first step. A member-step boundary holds back an NSG write when the NSG lies in the VNet of one of the step's network interfaces, because NSG rules there reference the Managed ASG itself, or when the write changes the decision of a flow to or from an IP of one of those network interfaces. An NSG in another VNet sees a network interface only by its IPs, so there the IP test is exact. Every other NSG write runs in any order relative to the member steps. A step is valid only if every combination of its atoms passes the step's test: in the first step no combination allows a flow that the Deployed state denies, and in the last step no combination allows a flow that the target denies. For a flow, only the atoms of its two endpoints count. Each network interface gets at most two writes, one per member step. Moving a VM between two ASG objects usually leaves first and joins last. Between two ASG objects that both deny, leaving first would open traffic through the rules below, so the engine joins first and leaves last.
- **A write that waits for another waits a Settle time.** `Succeeded` is not a data-plane barrier: traffic that a write closed still passed up to 0.22 s after an NSG PUT reported `Succeeded`, and up to 0.75 s after a network interface write (T4). Microsoft documents no propagation time ([Research: NSG and ASG rule semantics and limits](https://github.com/mfgAkilae/nsgfw/issues/2), U15). A write behind a Crossing-flow edge or behind a member-step boundary therefore starts only after the write before it has reported `Succeeded` (in a Terraform Environment, after Azure shows the previous step's target) and a Settle time has passed since. The Settle time is an instance setting, 10 s by default. Dependency edges (a Managed ASG before a reference to it, an association after its NSG, a deletion after the last member has left) concern only the control plane, which rejects a missing reference synchronously (T3), so they wait for `Succeeded` alone. After a crash the new lease holder waits the full Settle time again once it sees the earlier write done.
- **A Change set that cannot be ordered fails validation.** This happens when the edges form a cycle, between two Zones or around more, inside one Environment or across several, or when a member step fails its test in some combination of its atoms. The Preview names the flows, and the fix is to split the Change set into two Commits, like a limit breach.
- **A failed write delays only the writes that depend on it.** It is retried on its own. Writes with an edge from it wait, in later Deployments too, because every Deployment plans its edges from the Deployed state. There is no hold on Affected Zones and no override.
- **Edges cross Environments.** The two Zones of a flow can sit in different Environments, for example peered VNets in a platform Environment and in Production, and the member IPs of an ASG object can land in NSGs of another Environment. Crossing-flow edges and member-step boundaries therefore order writes across Environments too. A Commit still starts one Deployment per affected Environment, each with its own result. A write that waits for a write of another Environment's Deployment waits the same way: for `Succeeded`, in a Terraform Environment until Azure shows that step's target, and then the Settle time.
- **Every NSG that differs counts.** The engine compares every pair of Zones whose NSGs differ between the Deployed state and the latest Version, in every Environment, also where the Commit changes nothing. Example: Version 1290 opens a flow on an NSG in Production, and that Deployment has not finished. Version 1291 closes the same flow on an NSG in Non-production and changes nothing in Production. Inside one Environment the newer Deployment would supersede the older one and plan both writes. Across Environments, only this rule puts the closing write in Non-production first.
- **An edge into another Environment points at the NSG, not at a Deployment.** The waiting write starts once the Deployed state of the other NSG no longer lets the flow cross, whichever Deployment wrote it, and the Settle time has passed. Every Commit plans again the edges of the unfinished Deployments in the other Environments. They keep their Version and their writes, and the Deployment view notes the new plan. Like a superseding Deployment, the new plan waits until the writes in flight on the paired NSGs have ended.
- **A write that waits for another Environment has no time limit.** When the write it waits for fails, or that Deployment stops before its first write over Drift, a Policy finding or a limit, the waiting write keeps waiting, as inside one Environment. There is no time limit and no override. The ways out are a Retry in the other Environment, a Change set that fixes the cause, or a Revert of the Commit, which an admin can make an Emergency Commit. The next plan then drops the edge.
- **A Deployment that waits only for other Environments releases its lease.** It takes the state "waiting for" the other Environment, which is not a failure, and frees its Environment write lease, so that automatic Overwrite and other jobs of the Environment can run. It resumes on its own once the other write is done, and then waits the full Settle time, as after a crash.

## Considered Options

- **Keep ADR 0009.** Rejected. Interim contents cost a second write per NSG and count against the limits, holds block unrelated opening changes, and a Terraform Deployment needs two pull requests. Most Change sets need none of it.
- **No order at all.** Rejected. The five cases above open traffic that both the old and the new Version deny.
- **Edges from Dominance gaps,** the first form of this ADR. A Dominance gap is a flow that the destination's inbound NSG rules allow and the source's outbound NSG rules deny. A gap in the target only put the source first, and a gap in the Deployed state only put the destination first. Rejected after review. It is safe, but such a gap also arises when only one of the two NSGs changes, or when the target allows the flow, and then no order is needed. Over 12,000 random Change sets with all special cases mixed, it ordered 9,472 and rejected 867 as not orderable. The Crossing-flow rule ordered 2,956 and rejected 11, and neither opened traffic. An everyday Change set failed: with a strict Zone A and a Zone B that has the inbound Inherited default, replacing "allow A → B tcp/443" by "allow A → B tcp/22" got edges in both directions, although any order is safe.
- **Assuming what a service tag contains.** Rejected. When the engine assumed that `VirtualNetwork` holds every internal address and Azure resolved it differently, up to 1,204 of 9,000 random Change sets opened traffic in the check. Evaluating both ways opened none and rejected 97 as not orderable.
- **Remove the crossings through placement,** for example by letting the `VirtualNetwork` tag cover every Zone, or by letting a Retired NSG pass outbound traffic to the Internal address space. Rejected for now. It removes some crossings, but legacy NSGs and Inherited defaults still need the order, and it changes behaviour that ADR 0011 decided.
- **An interim content only for the Change sets that cannot be ordered.** Rejected. These are rare, and splitting the Change set needs no second algorithm.
- **An admin override for Change sets that cannot be ordered.** Rejected. An Emergency Commit of the closing part is the way out, as before.
- **ASG membership changes and Rule changes in separate Commits.** Rejected. Most Change sets that change members are safe in three steps.
- **Every member change that fits neither step fails validation,** as first decided. Rejected after the worked examples: moving a VM from one ASG object to another, a common edit, closes and opens at once, so it would always need two Commits, even when the Deployment writes no NSG.
- **Member IPs in the NSGs while membership changes.** Rejected. It costs two writes per NSG and runs into the address limits per side.
- **`AzureLoadBalancer` evaluated both ways,** as first decided. Rejected on 2026-11-10. The Platform exception sits above every Rule, so the case "the source is inside the tag" made every inbound flow that no Rule allows read "depends on the tag", and Import notes listed flows as opening that cannot open.
- **`Succeeded` as the barrier.** Rejected after T4: traffic that the earlier write closed still passed after it reported `Succeeded`.
- **A barrier from Azure's view of the rules,** the effective security rules of a network interface or IP flow verify. Rejected. Both read the configuration, not the data plane. Active probes would need agents in the customers' networks.
- **A Settle time on every edge.** Rejected. Dependency edges need only the control plane, and the wait would slow onboardings with new Managed ASGs and associations for no gain.
- **A Settle time per Environment.** Rejected. No measurement shows that regions differ, and the instance setting can be raised without a release.
- **No wait, with the gap named in the Preview.** Rejected. It breaks the guarantee for a window under a second, which the Settle time closes for 10 s per step boundary.
- **One membership atom per write.** Rejected. Parallel writes on different network interfaces still combine, so the combination test is needed anyway, and k atoms on one network interface cost k writes in a row.
- **Cutting a failing member step into single-atom writes with a Settle time between them.** Rejected. It needs a search for an order, more writes and more time, for cases that only arise with deny Rules on ASG objects. Splitting the Change set covers them.
- **Leave first, join last for every change that fits neither step,** as decided after the worked examples. Rejected: a move between two ASG objects that both deny opens traffic in the interim "in neither ASG" and would always need two Commits. The rule by own effect gives leave-first in the common case anyway.
- **Treating a private endpoint write as a whole once a measurement shows it.** Rejected. The atom model costs no extra writes, so a second rule would save nothing. Moot since 2026-11-10: the tool writes no private endpoint membership.
- **One IP configuration as the atom.** Rejected on 2026-11-10. Azure rejects the network interface when its IP configurations reference different ASGs, so no write can change one IP configuration alone.
- **Edges only inside one Environment,** with a Crossing flow between Environments failing validation. Rejected on 2026-11-10. The second Commit of the split could be committed only once the first Deployment is done, in a Terraform Environment perhaps days later. And with every differing NSG counted, a Commit that only closes traffic, an Emergency Commit too, would fail validation while another Environment has an unfinished Deployment that crosses it.
- **Ordering the Environments of a Commit as a whole.** Rejected on 2026-11-10. A write would wait for a whole Deployment instead of one write, pull requests included, and two flows in opposite directions between two Environments would form a cycle although the single writes have an order.
- **Comparing only the pairs whose NSGs the Commit changes.** Rejected on 2026-11-10. In the example above the flow would open for a moment although Version 1291 closes it.
- **An edge bound to one write of one Deployment.** Rejected on 2026-11-10. Once a newer Commit supersedes that Deployment, the edge would need a rule for where it moves.
- **A Commit that supersedes the unfinished Deployments of every Environment it shares an edge with.** Rejected on 2026-11-10. Production would show "superseded by Version 1291" although that Version changes nothing there.
- **A time limit or an admin override for a write that waits for another Environment.** Rejected on 2026-11-10, as inside one Environment: both would open traffic that the Deployed state and the target deny.
- **Holding the lease while waiting for another Environment.** Rejected on 2026-11-10. A pull request in a Terraform Environment can stay open for days, and automatic Overwrite and every other job of the waiting Environment would stall with it.
- **Ending the waiting Deployment as failed.** Rejected on 2026-11-10. Nothing in it failed, and it would need a Retry by hand.
- **Every NSG write between the member steps,** as first decided. Rejected on 2026-11-10. Across Environments one failed network interface write in Production would hold back every NSG write of the Commit in Non-production, closing ones too.
- **The IP test alone, also in the network interface's own VNet.** Rejected on 2026-11-10. NSG rules there reference the Managed ASG, so a write that adds a deny above an existing allow for that ASG would let a join open a flow for a moment.

## Consequences

- Most Deployments write each NSG once, in any order. The Preview shows the edges, the number of steps and the expected wait, the number of step boundaries times the Settle time, edges into other Environments included. A Deployment without edges and member steps waits nothing. One with member steps and one Crossing-flow edge has three boundaries and waits 30 s by default. The Settle time adds no writes, and the atom model adds none either.
- An NSG that waits for another waits as a whole, with every change in it, also the ones that close other traffic. No interim content brings those forward. The Preview and the Deployment view show what a waiting write holds back.
- In a Terraform Environment a Deployment is one pull request when its plan has no edges and no member steps. Otherwise each step of the order is its own pull request, opened once Azure shows the previous target and the Settle time has passed. A step that waits for a write in another Environment is its own pull request too, opened once that write is done and the Settle time has passed. Inside one pull request Terraform may write the atoms of a step in any order, which the atom model already assumes. The repository's HCL needs no `depends_on` for this.
- The first Commit to an NSG adopted in place has the legacy NSG as its Deployed state, and its Crossing flows order the writes. The interim content through the Import mapping of ADR 0011 is no longer needed.
- The engine computes Crossing flows, edges and member steps as pure functions of the Deployed state and the target. They depend on Azure state such as ASG members, like the NSG contents do. A Crossing flow needs both NSGs to differ between the Deployed state and the latest Version, so the engine compares only pairs of Zones whose NSGs both differ, in any Environment. The plan of a Deployment therefore reads the Deployed state of other Environments, and the engine functions stay pure. The combination test of a member step grows with the atoms of a flow's two endpoints. When no deny NSG rule references the ASGs of those atoms, membership only adds or only removes allowed flows, so the states before and after the step suffice. How the engine does both at the design target is open in [Grilling: Server internals at the design target](https://github.com/mfgAkilae/nsgfw/issues/30).
- The Deployment view shows both ends of an edge between Environments. The waiting write names the NSG, Zone and Environment it waits for, that write's Version and state (waiting, failed with its error code, stopped over Drift) and the flow. The other end says which write in which Environment waits for it. Everyone who sees the waiting write sees all of this, because the other Zone already appears in the Rule they can read. The link into the other Deployment view opens only with read access there. The Environment's status card shows "waiting for" the other Environment in amber. There is no alert of its own, because the failure in the other Environment raises one already.
- Deployed state that is itself a mix of Versions is fine: each Deployment bounds what a state allows by the Deployed state and the target, so no state allows a flow that every Version involved denies.
- The guarantee assumes that one NSG PUT takes effect as a whole (T2, 60 observations; a rejected PUT applied nothing, T3), that a single membership atom takes effect as a whole for each IP of its network interface, that one subnet write that swaps the NSG takes effect as a whole, and that Azure applies a write on the data plane within the Settle time. [Task: Empirical check of subnet NSG swaps and private endpoint ASG writes](https://github.com/mfgAkilae/nsgfw/issues/33) measures the swap and the private endpoint writes before the design review.
- The nightly integration test re-measures T1 to T5 and the subnet swap. It fails when an NSG PUT or a swap does not take effect as a whole, a rejected PUT applies something, a priority collision is accepted, or a lag after `Succeeded` exceeds half the Settle time. It logs the interim states of membership swaps without failing, because the engine assumes them.
- The check has limits. Its model has three Zones and one ASG object, and it classifies the member change of a network interface as a whole, with the other network interfaces at their Deployed or target members. The atom model and its combination test are not in the prototype. A network interface with atoms in both member steps is written twice, each time with a full PUT without `If-Match`. The member steps were checked with known tag contents only. The scripts are on the prototype branch (`check.mjs`, `member-order.mjs`, and for the amended rule `crossing-compare.mjs`, `crossing-tags.mjs`, `crossing-members.mjs`).
