# The order of writes follows Crossing flows, not Tighten and Loosen phases

Status: accepted (2026-11-10, [Prototype: Translation engine worked examples](https://github.com/mfgAkilae/nsgfw/issues/22)). Supersedes [ADR 0009](0009-tighten-then-loosen-deployments.md). Amends [ADR 0010](0010-terraform-mode-data-contract-and-azure-observation.md) and [ADR 0011](0011-import-preserves-behaviour.md). Amended on the same day after a review of the check: the first form ordered writes by Dominance gaps, which is safe but orders and rejects far more Change sets than needed. The rule is now exact, service tags are evaluated both ways, and any cycle fails validation. Amended again on 2026-11-10 after the worked examples of [Prototype: Translation engine worked examples](https://github.com/mfgAkilae/nsgfw/issues/22): a member change that fits neither step is split into two writes, and the engine assumes only documented service-tag facts. The file name keeps the first wording.

[ADR 0009](0009-tighten-then-loosen-deployments.md) wrote every Deployment in a Tighten phase and a Loosen phase, with interim contents and holds, because a one-sided deny Rule could move between the source and the destination side. [ADR 0016](0016-destination-enforced-egress-and-deny-rules-on-both-sides.md) puts deny Rules on both sides. The engine prototype checked whether the order of writes still matters (prototype on the throwaway branch [`prototype/translation-engine-order-check`](https://github.com/mfgAkilae/nsgfw/tree/prototype/translation-engine-order-check/prototypes/translation-engine-order-check), result in the ticket).

**The argument.** A flow between two Zones passes the source Zone's outbound and the destination Zone's inbound NSG rules, and a Deployment replaces each Managed NSG as a whole. While a Deployment runs, each of the two NSGs holds its old or its new content. A state can allow a flow that both the Deployed state and the target deny in exactly one way: one NSG denied the flow before and allows it now, the other allowed it before and denies it now, and the one that opens is written first. A flow with one Zone endpoint passes one Managed NSG, so no order can affect it.

**What the check found.** With the placement of ADR 0016, both NSGs usually agree on a flow, so nothing crosses. Over random Change sets with every mix of old and new NSG contents per Zone, no state opened traffic for Zones, CIDRs, hosts, any, ASG objects with fixed members, both Egress postures, posture changes, IPv6 Zones outside the Internal address space, outbound Inherited defaults and three Versions in flight. Flows cross in five cases, each with a worked example: a Rule with a service tag on one side (it lands on one side only), the Inherited default "inbound from `VirtualNetwork`" with a strict source, a removed Zone (its Retired NSG denies outbound), a legacy NSG before onboarding, and ASG membership, which is a write to a network interface and not part of any NSG. As a control, ADR 0009's own deny-flip example opens traffic under ADR 0004's placement and stays closed under ADR 0016.

We decided:

- **Writes have no phases.** A Deployment writes in dependency order (a new NSG or Managed ASG before a reference to it, an association after its NSG) and otherwise in any order, in parallel where the limits allow.
- **Crossing flows add edges.** A **Crossing flow** is a flow between two Zones that one of the two Managed NSGs denies in the Deployed state and allows in the target, while the other allows it in the Deployed state and denies it in the target. The NSG that closes the flow is written before the NSG that opens it. Nothing else orders NSG writes.
- **A service tag is evaluated both ways.** The engine cannot read what `VirtualNetwork` contains for an NSG, and the Inherited defaults and legacy NSGs use that tag. For each flow and each of the two NSGs, the engine therefore evaluates both cases, the address inside the tag and outside it, and takes the edges of all cases together. It assumes only what Microsoft documents: the address spaces of the NSG's own VNet and of directly peered VNets are inside `VirtualNetwork` and outside `Internet`. Every other tag, `AzureLoadBalancer` and the Azure service tags included, is evaluated both ways.
- **ASG membership is written in three steps.** First, the member changes that only close traffic under the Deployed NSG contents. Then the NSG writes, with their edges computed against the members as they are after that first step. Last, the remaining member changes, each of which must only open traffic under the target NSG contents. A member change that fits neither step as one write is split into two writes on the same network interface: it leaves ASGs in the first step, which must only close, and joins ASGs in the last step, which must only open. In between the network interface is in neither ASG, which only closes.
- **A Change set that cannot be ordered fails validation.** This happens when the edges form a cycle, between two Zones or around more, or when a member change fits no step, even split into leaving and joining. The Preview names the flows, and the fix is to split the Change set into two Commits, like a limit breach.
- **A failed write delays only the writes that depend on it.** It is retried on its own. Writes with an edge from it wait, in later Deployments too, because every Deployment plans its edges from the Deployed state. There is no hold on Affected Zones and no override.

## Considered Options

- **Keep ADR 0009.** Rejected. Interim contents cost a second write per NSG and count against the limits, holds block unrelated opening changes, and a Terraform Deployment needs two pull requests. Most Change sets need none of it.
- **No order at all.** Rejected. The five cases above open traffic that both the old and the new Version deny.
- **Edges from Dominance gaps,** the first form of this ADR. A Dominance gap is a flow that the destination's inbound NSG rules allow and the source's outbound NSG rules deny. A gap in the target only put the source first, and a gap in the Deployed state only put the destination first. Rejected after review. It is safe, but such a gap also arises when only one of the two NSGs changes, or when the target allows the flow, and then no order is needed. Over 12,000 random Change sets with all special cases mixed, it ordered 9,472 and rejected 867 as not orderable. The Crossing-flow rule ordered 2,956 and rejected 11, and neither opened traffic. An everyday Change set failed: with a strict Zone A and a Zone B that has the inbound Inherited default, replacing "allow A → B tcp/443" by "allow A → B tcp/22" got edges in both directions, although any order is safe.
- **Assuming what a service tag contains.** Rejected. When the engine assumed that `VirtualNetwork` holds every internal address and Azure resolved it differently, up to 1,204 of 9,000 random Change sets opened traffic in the check. Evaluating both ways opened none and rejected 97 as not orderable.
- **Remove the crossings through placement,** for example by letting the `VirtualNetwork` tag cover every Zone, or by letting a Retired NSG pass outbound traffic to the Internal address space. Rejected for now. It removes some crossings, but legacy NSGs and Inherited defaults still need the order, and it changes behaviour that ADR 0011 decided.
- **An interim content only for the Change sets that cannot be ordered.** Rejected. These are rare, and splitting the Change set needs no second algorithm.
- **An admin override for Change sets that cannot be ordered.** Rejected. An Emergency Commit of the closing part is the way out, as before.
- **ASG membership changes and Rule changes in separate Commits.** Rejected. Most Change sets that change members are safe in three steps.
- **Every member change that fits neither step fails validation,** as first decided. Rejected after the worked examples: moving a VM from one ASG object to another, a common edit, closes and opens at once, so it would always need two Commits, even when the Deployment writes no NSG.
- **Member IPs in the NSGs while membership changes.** Rejected. It costs two writes per NSG and runs into the address limits per side.

## Consequences

- Most Deployments write each NSG once, in any order. The Preview shows the edges and the number of steps.
- An NSG that waits for another waits as a whole, with every change in it, also the ones that close other traffic. No interim content brings those forward. The Preview and the Deployment view show what a waiting write holds back.
- In a Terraform Environment a Deployment is one pull request when its plan has no edges and no member steps. Otherwise each step of the order is its own pull request, opened after Azure shows the previous target. The repository's HCL needs no `depends_on` for this.
- The first Commit to an NSG adopted in place has the legacy NSG as its Deployed state, and its Crossing flows order the writes. The interim content through the Import mapping of ADR 0011 is no longer needed.
- The engine computes Crossing flows, edges and member steps as pure functions of the Deployed state and the target. They depend on Azure state such as ASG members, like the NSG contents do. A Crossing flow needs both NSGs to change, so the engine compares only pairs of Zones whose NSGs both change in the Deployment. How it does that at the design target is open for the engine design.
- Deployed state that is itself a mix of Versions is fine: each Deployment bounds what a state allows by the Deployed state and the target, so no state allows a flow that every Version involved denies.
- The guarantee still assumes that one NSG PUT and one network interface write each take effect as a whole. [Task: Empirical checks of undocumented Azure behaviour](https://github.com/mfgAkilae/nsgfw/issues/24) checks the NSG PUT.
- The check has limits. Its model has three Zones and one ASG object; a network interface in several ASG objects changes several memberships in one write, which the classification takes as one change and splits only when it fits neither step. A split change writes the network interface twice, each time with a full PUT without `If-Match`. The member steps were checked with known tag contents only. The scripts are on the prototype branch (`check.mjs`, `member-order.mjs`, and for the amended rule `crossing-compare.mjs`, `crossing-tags.mjs`, `crossing-members.mjs`).
