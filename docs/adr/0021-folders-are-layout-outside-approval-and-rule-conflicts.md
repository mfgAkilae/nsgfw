# Folders are layout, outside Approval and Rule conflicts

Status: accepted (2026-11-10, [Grilling: Folders in Import, Rebase and Versions](https://github.com/mfgAkilae/nsgfw/issues/34)). Amends [ADR 0007](0007-isolated-change-sets-with-optimistic-rebase.md) (Folder conflicts, and where a placed Rule lands at Rebase) and [ADR 0011](0011-import-preserves-behaviour.md) (where imported Rules land).

The map owner added Folders to the Rule base in [Prototype: Console UI](https://github.com/mfgAkilae/nsgfw/issues/25). A Folder is a named, contiguous run of Rules, one level deep. It carries only its name and has no effect on translation. Import, Rebase and Version storage were designed before Folders existed. Folders also run into two earlier rules from [Grilling: Change sets, concurrency and approval](https://github.com/mfgAkilae/nsgfw/issues/15). First, any edit to a Submitted or Approved Change set resets its Approvals. Second, edits without effect on traffic need the same Approval as any other edit (point 15). A Change set without Affected Zones falls under the instance default, four-eyes. A Rule rename needs Approval because it changes the NSG rule description in Azure. A Folder never reaches Azure or the Data contract.

We decided:

- **A Folder is layout.** It has a Folder ID that never changes and is never reused. In Recovery mode the Folder ID sequence jumps by the reserve like the other ID sequences ([ADR 0019](0019-instance-identity-in-the-database-and-recovery-mode.md)); no Folder ID reaches Azure. Folder names are unique, case-insensitive. A Folder may be empty, and it then holds a position of its own. A Version stores each Folder with its ID, name and position, and the Folder of each Rule. A Change set stores operations on Folder IDs (create, rename, remove, move) and the Folder of each placement. The Folder of a Rule is part of the Rule's position, not of its content.
- **Folder edits need no Approval and keep Approvals.** Creating, renaming and removing a Folder are Folder edits, and so is moving a Rule in or out of a Folder at the same position. A Change set that holds only Folder edits needs no Approval: any person with the editor Role in any Scope commits it. This is an explicit exception to the instance default. The Commit creates a Version without a Deployment. A Folder edit in a Submitted or Approved Change set keeps its state and its Approvals, and the Commit dialog lists the Folder edits made since the Approval.
- **Moving a Folder moves its Rules.** Each Rule of the Folder counts as moved. The order check at Rebase covers it, and its Affected Zones need Approval.
- **Folder conflicts at Rebase.** Two Change sets that rename, move or remove the same Folder conflict. An Author resolves the conflict, and a resolution that moves no Rule keeps the Approvals. A Rule that moves in or out does not change the Folder, so two Change sets can fill the same Folder without a conflict. The Folder of a Rule never conflicts with an edit of the Rule's fields. It conflicts only with another change to the same Rule's position or Folder. If one side removed a Folder and the other put Rules into it, the Rebase is clean: the Rules stay where they are, outside every Folder, and the Change set shows a notice. A duplicate Folder name after a Rebase, Restore or Revert is a validation error.
- **Where a placed Rule lands at Rebase.** This applies to every Rule that a Change set inserted or moved. The Rule lands after the nearest Rule that stood above it in the base Version and still exists. If the Rule has a Folder that still exists, only that Folder's Rules count, and with none left it goes to the top of the Folder. A Rule without a Folder never lands inside a Folder: it goes after that Folder's end. The order check then decides whether the new position conflicts.
- **Restore and Revert carry Folders.** A Restore brings back the Folders of its Version, with ID, name and Rules, and removes the Folders created since then. A Revert undoes its Commit's Folder edits. It removes a created Folder and leaves the Folder's Rules in place. It undoes a rename, and it turns a Folder move into a move of the Folder's Rules back. A removed Folder returns around its former Rules if they still stand together and in no other Folder; otherwise the Revert conflicts. It also conflicts when a later Commit changed the same Folder. A Restore or Revert that differs only in Folders needs no Approval.
- **Import creates no Folders.** Among the orders that fit, the constraint merge chooses the lowest position outside every Folder. An imported Rule stands inside a Folder only when the constraints force it there, and an info Import note says so. Any order that fits gives the same verdicts. An Author who puts an imported Rule into a Folder pins its position, as a move by hand would.
- **Reading and audit follow the Rules.** Under the read filter by Coverage ([ADR 0012](0012-access-follows-coverage.md)), a person sees a Folder that holds a Rule they may read, and every empty Folder. Counts include only the Rules they may read, and they edit only the Folders they see. An audit entry for a Folder edit carries the Scopes of the Rules whose Folder changes. An edit to an empty Folder carries the instance Scope.

## Considered Options

- **The Folder as an ordinary Rule field.** Rejected. Tidying up Folders would then conflict with every substantive edit of the same Rule and reset its Approvals.
- **Folder edits reset Approvals like every other edit.** Rejected. Tidying up would cost a new Approval, although no Managed NSG changes.
- **Resolving Folder conflicts automatically, in favour of the latest Version or of the Change set.** Rejected. One side's edit would be lost without anyone deciding. Such conflicts are rare.
- **A narrower Approval for a Folder move,** limited to the Rules whose order changes relative to an overlapping Rule with the other action. Rejected. A move is an edit of the moved Rule ([ADR 0012](0012-access-follows-coverage.md)).
- **A Folder per onboarded Zone, or per onboarding Change set, from Import.** The map owner rejected both. The merge often splits a Zone's imported Rules across existing Rules, so such a Folder would not stay contiguous, and administrators sort imported Rules themselves.
- **Folders identified by name.** Rejected. Rebase, Revert and the audit log would lose a Folder's identity when it is renamed.
- **A Restore that keeps today's Folders.** Rejected. A Restore brings back the order, and Folders are part of it.

## Consequences

- A Rule rename needs Approval and a Folder rename does not. This is deliberate: a Folder never reaches Azure, the Data contract or an NSG rule description. The JSON export of a Version holds its Folders.
- A Folder-only Commit touches no Environment. It starts no Deployment, changes no `nsgfw-version` tag and never waits for an open Re-translation.
- Change sets that the tool prepares (expiry, Adopt, Re-translation) never edit Folders.
- Folders ship in a later MVP stage after the small profile. Adding them later migrates nothing, because every Rule then starts outside every Folder.
