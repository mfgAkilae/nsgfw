# ASG objects: one Managed ASG per VNet, member IPs everywhere else

Status: accepted (2026-11-09, [Grilling: ASG model and NIC membership](https://github.com/mfgAkilae/nsgfw/issues/14)). Amended on 2026-11-09 by [Grilling: Review round on placement, egress posture and MVP shape](https://github.com/mfgAkilae/nsgfw/issues/27). Amended on 2026-11-10 by [Prototype: Translation engine worked examples](https://github.com/mfgAkilae/nsgfw/issues/22), and by [Grilling: ASG membership of private endpoints and multi-IP network interfaces](https://github.com/mfgAkilae/nsgfw/issues/39) after [Task: Empirical check of subnet NSG swaps and private endpoint ASG writes](https://github.com/mfgAkilae/nsgfw/issues/33) (T9). Amended on 2026-11-12 by [Grilling: ASG membership on IPv6 IP configurations](https://github.com/mfgAkilae/nsgfw/issues/42) after [Task: Empirical check of ASGs on dual-stack network interfaces](https://github.com/mfgAkilae/nsgfw/issues/41) (T10). Amended on 2026-11-12 by [Review: Grill review of the complete design package](https://github.com/mfgAkilae/nsgfw/issues/23): any editor drafts the switch for automatic adoption as an Object edit, and an ASG tagged by another Instance can back an External ASG object, or be adopted in place through a Handover.

The brief says the tool creates and manages ASGs, including NIC membership. Azure restricts ASGs more than firewall administrators expect. All members of one ASG must sit in one VNet. An NSG rule with ASGs on both sides needs all their members in one VNet. Microsoft's troubleshooting page also says that an NSG and the members of the ASGs it references must be in the same VNet. Whether a reference across a peering works is not documented ([Research: NSG and ASG rule semantics and limits](https://github.com/mfgAkilae/nsgfw/issues/2), U11). In hub-and-spoke networks, most flows cross VNets. Membership is also hard to write for some resource types. Scale sets keep it in the model, and existing instances pick it up only through the upgrade policy. AKS accepts it only through the AKS API. In Terraform, both exist only inline in resources that other repositories own ([Research: ARM and Resource Graph behaviour for NSG deployment](https://github.com/mfgAkilae/nsgfw/issues/4), [Research: Terraform azurerm modeling of NSGs, associations and ASGs](https://github.com/mfgAkilae/nsgfw/issues/6)).

We decided on two kinds of Address objects backed by ASGs:

- An **ASG object** has a static list of ASG members (network interfaces and private endpoints) that administrators change only through Change sets. The tool writes the network interfaces into one Managed ASG per VNet that holds them, so one object such as "WebServers" can span many spokes. A network interface is a member as a whole, with all its IP addresses. The tool writes the Managed ASGs on all its IPv4 IP configurations at once, because Azure requires every IPv4 IP configuration of a network interface to reference the same ASGs, and never on its IPv6 IP configurations, whose ASGs it leaves as they are. Microsoft does not document that requirement: [Task: Empirical check of subnet NSG swaps and private endpoint ASG writes](https://github.com/mfgAkilae/nsgfw/issues/33) measured it for all IP configurations, and [Task: Empirical check of ASGs on dual-stack network interfaces](https://github.com/mfgAkilae/nsgfw/issues/41) narrowed it to the IPv4 ones. Azure accepts other ASGs on an IPv6 IP configuration than on the IPv4 ones (T10, undocumented), and the Terraform association resource writes IPv4 IP configurations only ([Grilling: Terraform mode workflow](https://github.com/mfgAkilae/nsgfw/issues/17), point 13), so both modes write the same membership. Private endpoints are never written into a Managed ASG: the engine writes their private IPs on every NSG, also inside their VNet.
- An **External ASG object** stands for exactly one Unmanaged ASG. Others own its membership. The tool reads the members, for example scale-set or AKS node interfaces, but never writes them. A network interface is a member when its IPv4 IP configuration is in the ASG; then it is a member as a whole, with all its IP addresses. What its IPv6 IP configuration holds does not count. A network interface that is in the ASG only through its IPv6 IP configuration is no member, and the tool warns about it on the object and in Import, because the ASG reference still matches its IPv6 address.

On the NSG of a Zone, the Translation engine references an ASG only when the ASG's members are in that Zone's VNet. Everywhere else, it writes the members' private IPv4 and IPv6 addresses as a prefix list in its own partition. It does the same on Zones whose service does not support ASGs in NSG rules (PostgreSQL flexible server), and on every Zone that holds at least one private endpoint, whatever its network policies, for every ASG object and External ASG object. A member's IPv6 addresses go through the IP fallback on every NSG, also inside the ASG's VNet, so an ASG reference stands for IPv4 only. Microsoft documents connection failures when an ASG that the NSG of a private endpoint subnet references has more than 50 IP configurations ([private endpoint limitations](https://learn.microsoft.com/en-us/azure/private-link/private-endpoint-overview#limitations), page date 2026-08-11, retrieved 2026-11-10), and an External ASG object can grow past that outside any Change set. It keeps this fallback even if an empirical check shows that references across a peering work, because that behaviour is undocumented and depends on the peering.

## Considered Options

- **One ASG object is exactly one ASG, in one VNet.** Rejected. It maps 1:1 to Azure and makes Import trivial. But administrators would need one object per spoke and an Address group to combine them, so they would have to know VNet boundaries the tool is meant to hide.
- **Forbid ASG objects in Rules whose other side is in another VNet.** Rejected. In hub-and-spoke networks this makes ASG objects almost useless.
- **Reference the ASG across a peering where Azure accepts it.** Rejected. It would avoid member IPs on far-side NSGs, but it rests on undocumented behaviour, and the NSG content would depend on peering state.
- **Dynamic membership by Azure tag or rule.** Rejected for the MVP. The tool would either write memberships without Approval or put every match change into a Change set. External ASG objects cover dynamic cases such as autoscaling and application teams that manage membership in their own IaC.
- **Only tool-managed ASGs, as the brief literally says.** Rejected. Import would have to take over every existing ASG and fight its owner's IaC. Scale sets and AKS node pools could never be members.
- **Private endpoints in Managed ASGs, with the approval right where Azure asks for it.** Rejected on 2026-11-10. A write that changes only the ASGs of a private endpoint whose connection was approved automatically fails with `LinkedAuthorizationFailed` unless the writer holds `<provider>/<type>/privateEndpointConnectionsApproval/action` on the linked resource (T9). That right sits on another team's resource, often outside every Environment, Microsoft documents it only as what approves new connections, and with it the tool could open new paths to that resource's data ([ADR 0014](0014-operator-grants-azure-roles-tool-verifies.md)).
- **Only automatically approved private endpoints by IP,** manual ones in Managed ASGs. Rejected on 2026-11-10. Two rules for one kind of member, for no gain: a new private endpoint member goes through a Change set either way, and a changed IP is adopted on its own.
- **No automatically approved private endpoints in ASG objects.** Rejected on 2026-11-10. Most private endpoints are approved automatically.
- **IP configurations as ASG members.** Rejected on 2026-11-10. Azure rejects a network interface whose IP configurations reference different ASGs (`AllIpConfigurationsOnANicMustBelongToTheSameApplicationSecurityGroups`, [Task: Empirical check of subnet NSG swaps and private endpoint ASG writes](https://github.com/mfgAkilae/nsgfw/issues/33)).
- **Managed ASGs on every IP configuration in ARM mode.** Rejected on 2026-11-12. It would spare IPv6 prefixes inside the ASG's VNet. But an IPv6 leave kept its membership in the effective security rules for 150 s in 3 of 3 tries, until the IPv4 IP configuration left the same ASG (T10); whether it takes effect on the data plane is untested, so a member step could wait for a leave that does not apply. ARM mode and Terraform mode would also translate the same Rule base differently.
- **External ASG objects mirror Azure per IP configuration,** with the IP fallback listing only the IPs of IP configurations in the ASG. Rejected on 2026-11-12. Precise, but whether a dual-stack scale set or AKS node pool is reachable over IPv6 would depend on how another team's IaC sets the IPv6 IP configuration, and a member would no longer be a whole network interface.
- **Count the 50 members as an ASG limit that blocks the Change set,** or switch to the IP fallback only above 50. Rejected on 2026-11-10. An External ASG object grows past 50 outside any Change set, and a switch at a threshold changes NSG content at a count nobody sees. The fallback on every Zone with a private endpoint is predictable and keeps the limit out of reach.

## Consequences

- NSGs outside an ASG's VNet depend on its members' IPs. A changed IP, a deleted member or a change in an External ASG object's ASG makes them stale. The tool flags this like Drift.
  - The tool adopts three kinds of change on its own, without Approval and with an audit entry, as it disables an expired allow Rule ([ADR 0008](0008-approval-by-affected-zones.md)): what only closes traffic; a deleted member, which leaves every Rule of its object, deny Rules too; and a changed IP of a member, whose old IP leaves and whose new IP enters every Rule of its object. Azure can reuse an IP, so it must not stay allowed until someone approves. A reused IP belongs to no member, so the Rules treat it like any other address. A changed IP needs no Approval because the member itself is approved, as inside the ASG's VNet, where the reference follows the network interface.
  - The tool keeps one IP list per object, not per Rule, so it cannot take an IP out of the allow Rules only. The worked examples showed this for an object that is in an allow Rule and a deny Rule.
  - What else opens traffic, such as a new member of an External ASG object, goes into a Change set that the tool prepares for Approval.
  - An ASG object or an External ASG object can be set to adopt all member changes automatically. Switching this on or off is an Object edit in a Change set that any editor may draft; it needs no admin Role. Its Affected Zones are those of every Rule that uses the Object ([ADR 0008](0008-approval-by-affected-zones.md)) plus the Zones that hold its members. The Approval of that edit then covers future members, like a dynamic address group on a firewall. Without it, autoscaling across VNets would need an Approval for every new instance.
- Inside the ASG's VNet, a changed member IPv4 address needs no NSG change, and a new member in a Zone that is already covered works over IPv4 without one. Its IPv6 addresses enter the IP fallback, and where the ASG reference already lets its IPv4 address in without Approval (inside the ASG's VNet, on a Zone without a private endpoint), the tool adopts them on its own with an audit entry: the member is already approved, as for a changed IP. A dual-stack autoscaling node is therefore reachable over IPv6 without an Approval wherever it is over IPv4. Neither holds for private endpoint members, nor on a Zone that holds a private endpoint: there an ASG object behaves as across VNets, so a new member of an External ASG object needs an Approval unless its object adopts all member changes automatically.
- When a subnet gets its first private endpoint or loses its last, the NSG rules on its Zone switch between ASG references and member IPs. The members stay the same, so no flow changes, and the tool adopts the switch on its own with an audit entry ([ADR 0020](0020-versions-record-the-azure-inventory.md)).
- Managed ASGs get their name from an Environment's ASG naming pattern when the tool creates them, and keep it when the object is renamed. Their marker tags carry the instance ID and the Object ID.
- An Unmanaged ASG whose members are all network interfaces in an Environment can be adopted in place as a Managed ASG. One that holds a private endpoint cannot, because the tool could never take the private endpoint out again, so it would stay allowed after leaving the object; Import offers it as an External ASG object. A private endpoint that someone adds to a Managed ASG in Azure is flagged like Drift, without an Overwrite. An Unmanaged ASG that holds an IPv6 IP configuration cannot be adopted in place either: the tool would have to take it out with an IPv6 leave whose effect is unproven, or leave it in, and then the reference would still let the network interface in over IPv6 after it left the object. Import offers it as an External ASG object. A Managed ASG that someone puts on an IPv6 IP configuration is Drift, resolved by Overwrite only, which takes the ASG off again; the model has no IPv6 membership to adopt. The Preview of that Overwrite warns that the leave may take effect late, and the nightly integration test checks whether an IPv6 leave takes effect on the data plane. An ASG tagged by another Instance can be the ASG of an External ASG object without a Handover, because the tool only reads it. It can be adopted in place only through a Handover ([ADR 0019](0019-instance-identity-in-the-database-and-recovery-mode.md)).
- A Version stores the ASG members of every ASG object, so a rollback restores membership.
- Writing membership needs the optional Azure role `nsgfw ASG Writer` ([ADR 0014](0014-operator-grants-azure-roles-tool-verifies.md)).
- External ASG objects change the brief, which says that the tool creates and manages ASGs, including NIC membership. The tool only reads an External ASG object's ASG. The map owner confirmed the change on 2026-11-12 ([Review: Grill review of the complete design package](https://github.com/mfgAkilae/nsgfw/issues/23)).
