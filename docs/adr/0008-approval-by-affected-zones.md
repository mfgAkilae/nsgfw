# Approval by Affected Zones

Status: accepted (2026-11-09, [Grilling: Change sets, concurrency and approval](https://github.com/mfgAkilae/nsgfw/issues/15)). Amended on 2026-11-09 by [ADR 0016](0016-destination-enforced-egress-and-deny-rules-on-both-sides.md): the source side of a Rule counts only where the source NSG decides. Amended on 2026-11-10 by [Prototype: Translation engine worked examples](https://github.com/mfgAkilae/nsgfw/issues/22): a posture change affects only its Zone, and a change of the Internal address space affects every destination-enforced Zone. Amended by [ADR 0006](0006-asg-objects-one-managed-asg-per-vnet.md), [ADR 0020](0020-versions-record-the-azure-inventory.md) and [ADR 0021](0021-folders-are-layout-outside-approval-and-rule-conflicts.md), which add Commits without Approval. Amended on 2026-11-12 by [Review: Grill review of the complete design package](https://github.com/mfgAkilae/nsgfw/issues/23): this ADR holds the one list of Commits without Approval, and it says what a Change set of the tool does at the level none, what a Change set without Affected Zones needs, and that Roles and levels count as they stand at the Commit.

The brief makes Approval configurable per Scope, from none to four-eyes. One Rule can span Zones in several Environments with different requirements ([ADR 0001](0001-central-rule-base-across-environments.md)), so the tool needs a precise rule for which Scopes a Change set touches. Deriving them from the Preview is the obvious choice, but it misses effects. When an ASG member is added to an ASG object, the NSG rules inside the ASG's VNet already reference the ASG, so no NSG changes, yet new traffic reaches the Zone on the other side. A rebalance changes priorities in Zones whose traffic does not change.

We decided that Approval follows a Change set's **Affected Zones**. For every Rule that the Change set changes directly or through a changed Object or Zone, before and after the change, they are the Zones in the Coverage of its destination. From the Coverage of its source they are the Zones with a strict Egress posture, or all of them when the destination reaches outside Zones ([ADR 0016](0016-destination-enforced-egress-and-deny-rules-on-both-sides.md)). To these come the Zones of added or removed ASG members, the Zones that hold the members of an ASG object or External ASG object whose switch for automatic adoption changes ([ADR 0006](0006-asg-objects-one-managed-asg-per-vnet.md)), and the Zones it onboards, removes or changes. A change of a Zone's Egress posture or Inherited defaults affects only that Zone: the Rules that use the Zone do not count as changed through it, because what the Zone covers stays the same. A change of the Internal address space affects every destination-enforced Zone, because their egress allow uses it. Each Affected Zone needs the level its Scope requires: none, approver (an Author may approve) or four-eyes (an approver who is not an Author). The level is set on an Environment and can be overridden on a subscription, VNet or Zone, where the most specific setting wins in both directions. One approver's Approval counts for every Affected Zone in which that person holds the approver Role. An edit to a Rule without effect on traffic, such as a comment, gets no exemption; Folder edits are outside Approval ([ADR 0021](0021-folders-are-layout-outside-approval-and-rule-conflicts.md)). As a result, a Rule whose destination is any covers every Zone, and each of them needs its own level. A Rule from any to one Zone needs only that Zone and the strict Zones.

A Change set without Affected Zones needs the Approval of an approver in the instance Scope, at the instance default level. That level is four-eyes unless an instance admin changes it. At the level none, its committer needs the editor Role in the instance Scope. Where a rule names an admin for such a Change set, it means an admin in the instance Scope. A Change set that holds only Folder edits stays exempt ([ADR 0021](0021-folders-are-layout-outside-approval-and-rule-conflicts.md)).

Roles and Approval levels are evaluated at the Commit. An Approval counts only for the Zones in which its giver holds the approver Role at that moment, and the level that counts is the one in force then. For a scheduled or queued Commit, the person who scheduled it must hold the needed Roles when it runs. When something is missing, the Commit does not run. The Change set stays Approved, or returns to Submitted when an Approval is missing. It loses its schedule and names what is missing.

A Change set that the tool prepared commits once its Approval is complete, at the levels approver and four-eyes. At the level none it does not commit on its own. It waits in the inbox until one person who holds the editor Role in every Affected Zone at the level none commits it, as [ADR 0012](0012-access-follows-coverage.md) says for any Commit; an admin with those Roles can do it. Where a Change set of the tool has Affected Zones at several levels, each Zone follows its own level: the Zones at approver or four-eyes need their Approval, and a person who holds the editor Role in the Zones at the level none commits. The tool commits on its own only when no Affected Zone is at the level none. This holds for an expired deny Rule, an Adopt outside the cases below, a Re-translation and the Revert of a rejected Emergency Commit.

These Commits need no Approval, at every level. This list is the one place that names them all.

1. **The expiry of an allow Rule.** The tool disables the Rule and commits, because disabling an allow Rule can never open traffic under first-match evaluation. An expired deny Rule only gets a Change set that the tool prepares for normal Approval.
2. **An Emergency Commit.** An admin commits without the required Approval, with a mandatory reason. It needs Approval afterwards, per Affected Zone, and a rejection makes the tool prepare a Revert.
3. **A Change set that holds only Folder edits** ([ADR 0021](0021-folders-are-layout-outside-approval-and-rule-conflicts.md)).
4. **The automatic Adopt cases of [ADR 0006](0006-asg-objects-one-managed-asg-per-vnet.md):** an Adopt that only closes traffic ([ADR 0020](0020-versions-record-the-azure-inventory.md)), a deleted ASG member (deny Rules included), a changed IP of an ASG member, the IPv6 addresses of a new member whose IPv4 is already let in, the switch between ASG references and member IPs when a subnet gets its first or loses its last private endpoint, and every member change of an ASG object or External ASG object set to adopt automatically.
5. **Overwrite of Drift.** It writes the Deployed state back and has no Change set at all ([ADR 0026](0026-drift-is-resolved-by-adopt-or-overwrite.md)).

The tool makes the Commits of 1 and 4 itself. Neither closes a Tool path: the tool holds that one Rule or member change back until a person commits it with the usual confirmation and reason.

## Considered Options

- **Scopes from the Preview diff.** Rejected for the reasons above.
- **One approver for the whole Change set at the strictest level.** Rejected. A Rule across Environments would need an approver who holds the approver Role everywhere.
- **Overrides may only tighten the inherited level.** Rejected. A sandbox subscription inside a production management group would then need its own Environment.
- **Expiry handled only through Change sets with Approval.** Rejected. An expired allow Rule, for example a vendor's temporary access, would stay effective until someone approves.
