# Writes are ordered only by Crossing flows, with a Settle time

Status: accepted (2026-11-12, [Review: Grill review of the complete design package](https://github.com/mfgAkilae/nsgfw/issues/23)). Supersedes [ADR 0018](0018-write-order-from-dominance-gaps.md) together with [ADR 0024](0024-asg-membership-is-written-as-atoms-in-member-steps.md) and [ADR 0025](0025-the-write-order-spans-environments.md), and [ADR 0009](0009-tighten-then-loosen-deployments.md) together with [ADR 0022](0022-a-version-exists-from-its-commit-and-deployments-plan-from-the-deployed-state.md). First decided on 2026-11-10 in [Prototype: Translation engine worked examples](https://github.com/mfgAkilae/nsgfw/issues/22); the Settle time in [Grilling: Write order under data-plane lag and split ASG membership writes](https://github.com/mfgAkilae/nsgfw/issues/32).

A flow between two Zones passes the source Zone's outbound and the destination Zone's inbound NSG rules, and a Deployment replaces each Managed NSG as a whole. While a Deployment runs, each of the two NSGs holds its old or its new content. A state can allow a flow that both the Deployed state and the target deny in exactly one way: one NSG denied the flow before and allows it now, the other allowed it before and denies it now, and the one that opens is written first. A flow with one Zone endpoint passes one Managed NSG, so no order can affect it.

With deny Rules on both sides ([ADR 0016](0016-destination-enforced-egress-and-deny-rules-on-both-sides.md)) the two NSGs usually agree on a flow. The engine prototype found five cases in which flows cross: a Rule with a service tag on one side, the Inherited default "inbound from `VirtualNetwork`" with a strict source, a removed Zone (its Retired NSG denies outbound), a legacy NSG before onboarding, and ASG membership, which ADR 0024 covers.

We decided:

- **Writes have no phases.** A Deployment writes in dependency order (a new NSG or Managed ASG before a reference to it, an association after its NSG) and otherwise in any order, in parallel where the limits allow.
- **Crossing flows add edges.** A Crossing flow is a flow between two Zones that one of the two Managed NSGs denies in the Deployed state and allows in the target, while the other allows it in the Deployed state and denies it in the target. The NSG that closes the flow is written before the NSG that opens it. Nothing else orders NSG writes.
- **For a new association or a swap, the subnet write carries the edges.** The NSG of such a Zone takes effect through the subnet write, so that write carries the Crossing-flow and member-step edges and starts the Settle time. Its Deployed content is the NSG associated so far, or "allows everything" without one.
- **A service tag is evaluated both ways.** The engine cannot read what `VirtualNetwork` contains for an NSG, and the Inherited defaults and legacy NSGs use that tag. For each flow and each of the two NSGs, the engine evaluates both cases, the address inside the tag and outside it, and takes the edges of all cases together. It takes as fact only what Microsoft documents: the address spaces of the NSG's own VNet and of directly peered VNets are inside `VirtualNetwork`, and `AzureLoadBalancer` translates to the virtual IP of the host, 168.63.129.16, and includes only probe traffic, so no address of a Zone is inside it ([service tags overview](https://learn.microsoft.com/en-us/azure/virtual-network/service-tags-overview), page date 2026-09-16, retrieved 2026-11-09 for [Research: NSG and ASG rule semantics and limits](https://github.com/mfgAkilae/nsgfw/issues/2)). A peering counts only when it is Connected, allows virtual network access and covers the whole VNet; [ADR 0020](0020-versions-record-the-azure-inventory.md) says which inventory must hold it. The engine also takes these address spaces as outside `Internet`; for a peered VNet that is an assumption, not a documented fact. Every other tag is evaluated both ways.
- **A write that waits for another waits a Settle time.** `Succeeded` is not a data-plane barrier: traffic that a write closed still passed up to 0.22 s after an NSG PUT reported `Succeeded`, and up to 0.75 s after a network interface write ([Task: Empirical checks of undocumented Azure behaviour](https://github.com/mfgAkilae/nsgfw/issues/24), T4 in the [empirical checks](../research/empirical-checks.md)). Microsoft documents no propagation time ([Research: NSG and ASG rule semantics and limits](https://github.com/mfgAkilae/nsgfw/issues/2), U15). A write behind a Crossing-flow edge or a member-step boundary therefore starts only after the write before it has reported `Succeeded` (in a Terraform Environment, after Azure shows the previous step's target) and the Settle time has passed since. The Settle time is an instance setting, 10 s by default. Dependency edges concern only the control plane, which rejects a missing reference synchronously (T3), so they wait for `Succeeded` alone. After a crash the new lease holder waits the full Settle time again.
- **A write of a Zone that holds a private endpoint, its NSG write or the subnet write that associates its NSG, is followed by 30 s** instead of the Settle time when another write waits for it. This is a second instance setting, "Settle time for private endpoint Zones". The only measurement for private endpoints took effect 9.9 to 11.8 s after the response ([Task: Empirical check of subnet NSG swaps and private endpoint ASG writes](https://github.com/mfgAkilae/nsgfw/issues/33), T8), and no check measured an NSG PUT against private endpoint traffic.
- **A Change set that cannot be ordered fails validation.** This happens when the edges form a cycle, between two Zones or around more, inside one Environment or across several, or when a member step fails its test (ADR 0024). The Preview names the flows, and the fix is to split the Change set into two Commits, like a limit breach. A plan can also become not orderable after the Commit, for example when a peering disappears and the new tag cases close a cycle. The unfinished Deployment then stops in the state "not orderable" and names the flows. The ways out are a Change set that fixes the cause, or a Revert of the Commit, which an admin can make an Emergency Commit.
- **A failed write delays only the writes that depend on it.** It is retried on its own. Writes with an edge from it wait, in later Deployments too, because every Deployment plans its edges from the Deployed state. There is no hold on Affected Zones and no override. An NSG whose PUT is accepted and ends `Failed` counts as Drift until a GET shows the old or the new content.
- **Three measured behaviours carry the guarantee without a fallback.** One whole-NSG PUT takes effect as a whole (T2, 60 observations) and a rejected PUT applies nothing (T3), both from [Task: Empirical checks of undocumented Azure behaviour](https://github.com/mfgAkilae/nsgfw/issues/24). One subnet write that swaps the NSG takes effect as a whole (T7, 60 swaps, from [Task: Empirical check of subnet NSG swaps and private endpoint ASG writes](https://github.com/mfgAkilae/nsgfw/issues/33)). The design knows all three from measurement only. They are a named, accepted exception to "documentation before tests" ([Grilling: Review round on placement, egress posture and MVP shape](https://github.com/mfgAkilae/nsgfw/issues/27), point 19): they have a nightly test and no fallback. When the nightly test fails on one of them, the project publishes a release note, Health shows a warning from the next release on, and a Change set whose write plan has a Crossing-flow edge fails validation and must be split into two Commits until a fix ships.

The algorithm is in [the translation engine design](../design/translation-engine.md#plan-the-write-order), section "Plan: the write order".

## Considered Options

- **Keep the Tighten and Loosen phases of ADR 0009.** Rejected. Interim contents cost a second write per NSG and count against the limits, holds block unrelated opening changes, and a Terraform Deployment needs two pull requests. Most Change sets need none of it.
- **No order at all.** Rejected. The five cases above open traffic that both the old and the new Version deny.
- **Edges from Dominance gaps,** the first form of the rule and the wording in ADR 0018's file name. A Dominance gap is a flow that the destination's inbound NSG rules allow and the source's outbound NSG rules deny. Rejected. It is safe, but such a gap also arises when only one of the two NSGs changes, or when the target allows the flow, and then no order is needed. Over 12,000 random Change sets it ordered 9,472 and rejected 867 as not orderable. The Crossing-flow rule ordered 2,956 and rejected 11, and neither opened traffic.
- **Assuming what a service tag contains.** Rejected. When the engine assumed that `VirtualNetwork` holds every internal address and Azure resolved it differently, up to 1,204 of 9,000 random Change sets opened traffic in the check. Evaluating both ways opened none and rejected 97 as not orderable.
- **`Succeeded`, the effective security rules or IP flow verify as the barrier.** Rejected. Traffic still passed after `Succeeded` (T4), and the other two read the configuration, not the data plane. Active probes would need agents in the customers' networks.
- **A Settle time per Environment.** Rejected. Only one region was measured, and the instance setting can be raised without a release.

## Consequences

- Most Deployments write each NSG once, in any order, and wait nothing. The Preview shows the edges, the number of steps and the expected wait: the number of step boundaries times the Settle time. The Settle time adds no writes.
- An NSG that waits for another waits as a whole, with every change in it, also the ones that close other traffic. The Preview and the Deployment view show what a waiting write holds back.
- In a Terraform Environment a Deployment is one pull request when its plan has no edges and no member steps. Otherwise each step of the order is its own pull request, opened once Azure shows the previous target and the Settle time has passed.
- The first Commit to an NSG adopted in place has the legacy NSG as its Deployed state, and its Crossing flows order the writes.
- A Deployed state that is itself a mix of Versions is fine: each Deployment bounds what a state allows by the Deployed state and the target, so no state allows a flow that every Version involved denies.
- The nightly integration test re-measures T1 to T5 and the subnet swap. It fails when an NSG PUT or a swap does not take effect as a whole, a rejected PUT applies something, a priority collision is accepted, or a lag after `Succeeded` exceeds half the Settle time. It gets a private endpoint target with network policies enabled and a second region, because all measurements so far come from one region.
