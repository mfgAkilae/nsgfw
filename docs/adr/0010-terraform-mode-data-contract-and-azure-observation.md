# Terraform mode: the tool owns only a Data contract, and Azure decides success

Status: accepted (2026-11-09, [Grilling: Terraform mode workflow](https://github.com/mfgAkilae/nsgfw/issues/17)). Amended on 2026-11-10 by [Prototype: Translation engine worked examples](https://github.com/mfgAkilae/nsgfw/issues/22), [Task: Translation engine design doc with worked examples](https://github.com/mfgAkilae/nsgfw/issues/31) and [Prototype: Architecture proposal](https://github.com/mfgAkilae/nsgfw/issues/26). Amended on 2026-11-12 by [Review: Grill review of the complete design package](https://github.com/mfgAkilae/nsgfw/issues/23): rewritten in place in the terms of the write order, with four rules for a replacement HCL, the provider versions, and how the tool merges and batches pull requests.

In a Terraform Environment the tool must not write the resources it manages; the repository's pipeline does. Customer repositories differ: their own modules, one root module (own state, own pipeline) per subscription or landing zone, and different CI systems. Rendering HCL from templates would need a template engine, escaping, a sandbox and HCL validation, and the tool would own code that the Terraform team wants to review and lint in Git. A merged pull request or a green pipeline also does not say what reached Azure, so neither can tell the tool that a step of the write order ([ADR 0023](0023-writes-are-ordered-only-by-crossing-flows-with-a-settle-time.md)) is done.

We decided:

- **The tool writes data, not HCL.** Per root module it writes one deterministic JSON file, the **Data contract**: the target content of every Managed NSG (full rule list, tags, `flushConnection`), the NSG of every Zone's subnet, the Managed ASGs, their memberships, import entries for resources that already exist in Azure, a revision value and the data contract version. A path pattern per subscription places the files. The tool regenerates and overwrites them in every pull request and never touches anything else in the repository.
- **The repository owns the HCL that reads the Data contract.** The tool ships a default HCL once, in a bootstrap pull request at Environment onboarding: one `azapi_resource` per NSG with the complete rule list and `flushConnection`, `azapi_update_resource` on the subnet for the NSG association, `azurerm_application_security_group` and `azurerm_network_interface_application_security_group_association` for the Managed ASGs and their network interfaces, and `import` blocks with `for_each`. It has no resource for private endpoints, because they are never written into a Managed ASG ([ADR 0006](0006-asg-objects-one-managed-asg-per-vnet.md)). Any replacement must keep four rules:
  1. One resource holds the complete rule list of an NSG.
  2. The subnet's NSG is set in one subnet write.
  3. The NSG resource depends on the Managed ASG resources, the Managed ASG resource sets `lifecycle { create_before_destroy = true }`, and the network interface association references the Managed ASG resource. The Data contract names an ASG by its resource ID, so Terraform sees no dependency on its own. With the dependency, one apply creates a Managed ASG before an NSG rule references it. By default Terraform destroys a dependency before it updates the resource that depends on it. With `create_before_destroy` on the dependency, it updates the dependent resource first, so it updates the NSGs before it destroys a Managed ASG they referenced ([Terraform, `docs/destroying.md`](https://github.com/hashicorp/terraform/blob/v1.17.1/docs/destroying.md), retrieved 2026-11-12).
  4. Tags that others set on a Managed NSG or Managed ASG are kept. Only the marker tags belong to the tool, in both Deployment modes, and other tags are never Drift. The default HCL merges the Data contract's marker tags with the tags that exist.
- **The repository's pipeline runs plan and apply.** The tool never reads state or backend credentials. Approval happens in the tool before the Commit; whether a person also reviews the pull request is the repository's branch protection.
- **The tool merges what can merge at once, and requests auto-merge for the rest.** GitHub offers auto-merge only when the repository allows it and the pull request cannot merge at once ([GitHub Docs: Automatically merging a pull request](https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/automatically-merging-a-pull-request), retrieved 2026-11-12). Environment onboarding therefore checks whether the repository allows auto-merge and flags it when not. A pull request that is mergeable at once, with no required review or check pending, is merged by the tool itself; that bypasses no protection. The tool does this only when the Environment setting "merge pull requests automatically" is on; the setting is off until the operator switches it on. Otherwise the pull request waits for a person, and the Deployment view says so. Otherwise the tool requests auto-merge.
- **Success is observed in Azure.** After the merge, the tool reads every resource of the pull request and compares it with the target. Only a match updates the Deployed state and lets the next step start. If Azure does not match within the apply timeout, the rest is "merged, not applied".
- **One pull request per step of the write order.** A Deployment whose write order has no Crossing-flow edges and no member steps is one pull request. Otherwise each step is its own pull request, and the tool opens it once Azure shows the previous step's target and the Settle time has passed ([ADR 0023](0023-writes-are-ordered-only-by-crossing-flows-with-a-settle-time.md), [ADR 0024](0024-asg-membership-is-written-as-atoms-in-member-steps.md)). A step that waits for a write in another Environment is its own pull request too ([ADR 0025](0025-the-write-order-spans-environments.md)). Every pull request carries the whole Data contract of the root module, in which the resources of later steps still have their Deployed content. Deleting Managed ASGs rides in the last pull request. An Environment has at most one open nsgfw pull request, and a newer Deployment closes it as superseded.
- **A merged step is observed to its end.** A newer Deployment plans only after the observation of a merged step has ended, by a match or by the apply timeout. The Terraform stage watch keeps the Deployed state of a superseded step current.
- **The tool batches its own Commits per Terraform Environment:** at most one every 30 minutes. The Version exists from the Commit at once; only the Deployment to the Terraform Environment, that is its pull request, is batched. Commits that only close traffic go at once. Every newer Deployment closes the open pull request, so a steady flow of automatic Adopts would otherwise keep a pull request that waits for a person's review from ever merging.

## Considered Options

- **Rendered HCL through a template engine.** Rejected. The pull request would show literal HCL, but the tool would need escaping, a sandbox and HCL validation, and diffs would be larger.
- **HCL stored in the tool as an Environment setting.** Rejected. Admins would edit HCL in a web form, and the repository's review and lint tooling would see it only as generated output.
- **The tool runs plan, or plan and apply.** Rejected. It needs state and backend credentials, a Terraform binary in the image and, for apply, Azure write access in every Terraform Environment.
- **Merge, or a green pipeline, counts as deployed.** Rejected. A failed or partial apply would go unnoticed, and the next step of the write order would start too early.
- **One pull request for all steps, with a Preview warning or with `depends_on` edges.** Rejected. Between two ordered steps the tool must see the previous target in Azure and then wait the Settle time ([ADR 0023](0023-writes-are-ordered-only-by-crossing-flows-with-a-settle-time.md)). Neither can happen inside one apply.
- **Separate `azurerm_network_security_rule` resources.** Rejected. Priority shifts across them fail with `SecurityRuleConflict`, and the provider cannot order them.
- **`azurerm_subnet_network_security_group_association`.** Rejected. Replacing it detaches the old NSG before it attaches the new one, and the ALZ policy `Deny-Subnet-Without-Nsg` denies the subnet write in between.
- **A pull request of its own for new Managed ASGs.** Rejected on 2026-11-10. It needs no rule for the HCL, but it adds a pull request to every Deployment that creates an ASG, for an order that Terraform's graph gives within one apply.

## Consequences

- The Data contract changes the brief, which asks for generated Terraform code that follows templates configurable per Environment. The map owner confirmed the change on 2026-11-12 ([Review: Grill review of the complete design package](https://github.com/mfgAkilae/nsgfw/issues/23)).
- The tool does not parse the repository's HCL. Azure observation catches wrong content, but not wrong order. A repository HCL that breaks the rules above can break the guarantee of the write order ([ADR 0023](0023-writes-are-ordered-only-by-crossing-flows-with-a-settle-time.md)) without anyone noticing, so the documentation states them.
- Every apply of a root module reverts Drift on all tool resources in it. The Drift pre-check therefore covers every tool resource in the touched root modules, and Overwrite and Retry use pull requests that change only the revision value.
- Minimum versions: Terraform 1.7 or later (`import` with `for_each`) and azapi 2.x. For azurerm, the minimum is the lowest major that the nightly test runs. 4.x and 5.x are tested; 3.x is expected to work and is not tested. The default HCL is also tested on OpenTofu ([ADR 0002](0002-mit-licence-and-open-source-dependencies-only.md)).
- The Environment setting "Terraform templates" from [Grilling: Environment and tenancy model](https://github.com/mfgAkilae/nsgfw/issues/9) becomes: Git repository and base branch, path pattern, data contract version, auto-merge switch and apply timeout.
