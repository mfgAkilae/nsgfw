# Every Version records the Azure inventory it was translated against

Status: accepted (2026-11-10, [Grilling: Server internals at the design target](https://github.com/mfgAkilae/nsgfw/issues/30)). Amended on 2026-11-12 by [Review: Grill review of the complete design package](https://github.com/mfgAkilae/nsgfw/issues/23): a Change set pins the facts of an Azure resource that it references first, every Commit takes over the observed facts that change no translation, and a deleted Zone subnet and a subscription that leaves its Environment are flags outside Adopt.

The Translation engine needs facts about Azure besides the Rule base: the address spaces and peerings of VNets, the prefixes of subnets (also of subnets that are not Zones) and their `privateEndpointNetworkPolicies` setting, the IPs of network interfaces and private endpoints, the members of External ASG objects, and the Environment of each subscription ([ADR 0004](0004-place-rules-by-coverage.md), [ADR 0016](0016-destination-enforced-egress-and-deny-rules-on-both-sides.md)). These facts change outside the tool. If the engine read them live, a Commit could write NSG rules that differ from the Preview an approver saw ([ADR 0008](0008-approval-by-affected-zones.md)), and a new subnet prefix would change NSGs without anyone deciding it.

We decided:

- **Every Version records its Azure inventory.** The Preview, the Commit and the write plan translate against the Azure inventory of the Version they work on, never against live Azure. A Change set uses the Azure inventory of its base Version, and a Rebase moves it to the latest one. The existing NSGs at Import are not part of the Azure inventory; they live in the Import snapshot.
- **Pinned Azure facts.** A Change set that first references an Azure resource that the Azure inventory of its base Version does not hold (a new subnet, network interface, VNet or peering, or the ASG of a new External ASG object) pins that resource's facts from the observed Azure inventory into the Change set, as the Import snapshot does for NSGs. Such a resource changes no translation, so no Adopt would ever carry it into a Version, and a subnet created yesterday could not be onboarded. The Preview shows the pinned facts. When a pinned fact changes in the observed Azure inventory before the Commit, the tool pins the new value and resets the Approvals of the Affected Zones whose NSG rules change by it. At the Commit the pinned facts become part of the new Version's Azure inventory.
- **Every Commit takes over what changes no translation.** Every Commit also takes over from the observed Azure inventory the facts that change no translation of the Rule base: new peerings, subnets and network interfaces that nothing references.
- **A change in Azure that would change the translation enters only through Adopt.** The tool keeps an observed Azure inventory per Environment, refreshed by the Drift poll and the daily reconcile. When the observed Azure inventory changes the translation of the latest Version, the tool prepares a Change set. It commits on its own the automatic Adopt cases, which [ADR 0008](0008-approval-by-affected-zones.md) lists with the other Commits without Approval and [ADR 0006](0006-asg-objects-one-managed-asg-per-vnet.md) defines. [Grilling: Review round on placement, egress posture and MVP shape](https://github.com/mfgAkilae/nsgfw/issues/27), point 14, and [Grilling: Server internals at the design target](https://github.com/mfgAkilae/nsgfw/issues/30), point 6, decided them. Everything else needs the usual Approval.
- **Two flags stand outside Adopt.** A Zone whose subnet is deleted in Azure, and a subscription that leaves its Environment, are flags and not Adopts. The latest Version keeps the old facts. The tool skips the writes of the Zones concerned, prepares no Adopt for them and changes nothing on its own. A write that waits for a skipped write keeps waiting and shows "skipped" as the state of the other side. A person resolves the flag: removes the Zone, moves it to the Environment that its subscription now belongs to (re-home), or removes it from the Rule base only (forget).
- **An open Adopt blocks nothing.** Other Commits and Deployments go ahead with the Azure inventory of their Version, because the NSGs already in Azure have the same gap. The Preview marks the Zones concerned with "Azure differs, Adopt open".
- **The write plan trusts a peering only when both agree.** A documented tag fact (a directly peered VNet lies inside `VirtualNetwork`, [ADR 0023](0023-writes-are-ordered-only-by-crossing-flows-with-a-settle-time.md)) counts only when the Version's Azure inventory and the observed Azure inventory both hold the peering. The peering must also be Connected, allow virtual network access (`allowVirtualNetworkAccess`) and cover the whole VNet. Microsoft documents the peered VNet as part of the tag only while that access is allowed ([Create, change, or delete an Azure virtual network peering](https://learn.microsoft.com/en-us/azure/virtual-network/virtual-network-manage-peering), page date 2025-07-29, retrieved 2026-11-09, in the [research on NSG and ASG semantics](../research/nsg-asg-semantics-and-limits.md)). The review found no statement for a peering in another state or for a peering of single subnets. Otherwise the engine evaluates both cases. A peering removed in Azure after the Commit would otherwise hide a Crossing flow.

Whether a Version stores its Azure inventory as a full copy or as changes is part of the data model.

## Considered Options

- **Live Azure at the Commit.** Rejected. The NSG rules written could differ from the approved Preview, and Azure changes would reach NSGs without Approval.
- **Live Azure in the Preview, pinned at the Commit.** Rejected. The Preview of an ordinary Change set would show changes it did not cause, with Affected Zones that do not include them.
- **Block Commits while an Adopt is open.** Rejected. The Commit does not widen the gap, and blocking would stall unrelated work behind an Approval for a change made in Azure.
- **Only the Version's peerings in the write plan.** Rejected for the reason in the last point above.

## Consequences

- What an approver saw is what the Deployment writes for the Zones they approved, in content. Priorities and names can differ from the approved Preview after a Rebase. A Rebase resets the Approval of an Affected Zone when the NSG rules that the Change set writes for that Zone differ in content from the Preview that approver saw ([ADR 0007](0007-isolated-change-sets-with-optimistic-rebase.md)), and a pinned fact that changes resets the Approvals of the Affected Zones whose NSG rules change by it.
- Each Version is reproducible: the Rule base, its Azure inventory, the NSG rules of the previous Version and the engine version give the same NSG rules.
- An Azure change that alters the translation always produces a Change set, with Approval unless it is one of the automatic Adopt cases. A busy estate produces a steady flow of small Adopt Change sets.
- The tool stores two inventories: the observed one per Environment and the one each Version records. An Open Change set also stores its pinned Azure facts.
