# ASG membership is written as atoms in member steps

Status: accepted (2026-11-12, [Review: Grill review of the complete design package](https://github.com/mfgAkilae/nsgfw/issues/23)). Supersedes [ADR 0018](0018-write-order-from-dominance-gaps.md) together with [ADR 0023](0023-writes-are-ordered-only-by-crossing-flows-with-a-settle-time.md) and [ADR 0025](0025-the-write-order-spans-environments.md). First decided on 2026-11-10 in [Grilling: Write order under data-plane lag and split ASG membership writes](https://github.com/mfgAkilae/nsgfw/issues/32), and changed for private endpoints in [Grilling: ASG membership of private endpoints and multi-IP network interfaces](https://github.com/mfgAkilae/nsgfw/issues/39) and for IPv6 in [Grilling: ASG membership on IPv6 IP configurations](https://github.com/mfgAkilae/nsgfw/issues/42).

ASG membership is a write to a network interface and not part of any NSG, so the order of NSG writes in [ADR 0023](0023-writes-are-ordered-only-by-crossing-flows-with-a-settle-time.md) does not cover it. Azure does not apply such a write as a whole either: one network interface write that moved an IP configuration from one ASG to another passed through "in both" or "in neither" in 14 of 60 swaps ([Task: Empirical checks of undocumented Azure behaviour](https://github.com/mfgAkilae/nsgfw/issues/24), T5 in the [empirical checks](../research/empirical-checks.md)). "In neither" can fall through to the NSG rules below and open traffic that both the Deployed state and the target deny.

We decided:

- **A membership atom is one network interface joining or leaving one Managed ASG.** Its write sets the ASG on every IPv4 IP configuration of the interface at once, because Azure rejects a network interface whose IPv4 IP configurations reference different ASGs ([Task: Empirical check of subnet NSG swaps and private endpoint ASG writes](https://github.com/mfgAkilae/nsgfw/issues/33)). Azure may still apply the IP configurations one by one, but a flow touches one IP of the interface, so per flow the atom is applied or not.
- **IPv6 IP configurations and private endpoints are no atoms.** A member's IPv6 addresses reach NSGs through the IP fallback, so their joins and leaves are NSG writes, and a membership write sends the IPv6 IP configurations back with the ASGs they hold. An IPv6 leave kept its membership in the effective security rules until the IPv4 IP configuration left too ([Task: Empirical check of ASGs on dual-stack network interfaces](https://github.com/mfgAkilae/nsgfw/issues/41), T10), so a member step could not rely on it. The tool carries private endpoints by their IPs ([ADR 0006](0006-asg-objects-one-managed-asg-per-vnet.md)), so a new or removed private endpoint member changes NSG content only.
- **Azure may apply the atoms of a step in any combination,** inside one write and across parallel writes (T5). The plan assumes this instead of an order.
- **Each atom goes into one of two member steps, by its own effect.** An atom that, applied alone to the Deployed members, only closes traffic under the Deployed NSG contents goes into the first step. Every other atom goes into the last step. Between them come the NSG writes that the steps can affect, with their Crossing-flow edges computed against the members as they are after the first step. Each network interface gets at most two writes, one per member step.
- **A step is valid only if every combination of its atoms passes.** In the first step no combination allows a flow that the Deployed state denies, and in the last step none allows a flow that the target denies. For a flow, only the atoms of its two endpoints count. A step that fails in some combination makes the Change set not orderable: it fails validation and is split into two Commits (ADR 0023).
- **A member-step boundary holds back only the NSG writes it can affect.** It holds back an NSG write when the NSG lies in the VNet of one of the step's network interfaces, because NSG rules there reference the Managed ASG itself, or when the write changes the decision of a flow to or from an IP of one of those network interfaces. An NSG in another VNet sees a network interface only by its IPs, so there the IP test is exact. Every other NSG write runs in any order relative to the member steps. A write behind a boundary waits the Settle time (ADR 0023).
- **ASGs on the IPv4 IP configurations only of a dual-stack network interface are a measured behaviour with a fallback.** Cases 1 and 4 of T10 join the nightly test. If it fails, dual-stack members go fully through the IP fallback.

The algorithm is in [the translation engine design](../design/translation-engine.md#plan-the-write-order), section "Plan: the write order".

## Considered Options

- **Leave first, join last for every change that fits neither step.** Rejected. A move between two ASG objects that both deny opens traffic in the interim "in neither ASG" and would always need two Commits. The rule by own effect gives leave-first in the common case anyway.
- **One membership atom per write.** Rejected. Parallel writes on different network interfaces still combine, so the combination test is needed anyway, and k atoms on one network interface cost k writes in a row.
- **Atoms on every IP configuration, IPv6 included.** Rejected. An IPv6 leave stayed in the effective security rules until IPv4 left too, so a member step could wait for a leave that does not apply, and the output of ARM mode and Terraform mode would differ.
- **Every NSG write between the member steps.** Rejected. Across Environments one failed network interface write in Production would hold back every NSG write of the Commit in Non-production, closing ones too.
- **The IP test alone, also in the network interface's own VNet.** Rejected. NSG rules there reference the Managed ASG, so a write that adds a deny above an existing allow for that ASG would let a join open a flow for a moment.

## Consequences

- The atom model adds no writes: at most two per network interface in one Deployment. A Deployment with member steps and one Crossing-flow edge has three step boundaries and waits 30 s by default.
- Moving a VM between two ASG objects usually leaves first and joins last. Between two ASG objects that both deny, leaving first would open traffic through the rules below, so the engine joins first and leaves last.
- An ASG reference stands for IPv4 only, in both Deployment modes.
- Inside one pull request Terraform may write the atoms of a step in any order, which the atom model already assumes. The repository's HCL needs no `depends_on` for this.
- The combination test grows with the atoms of a flow's two endpoints. When no deny NSG rule references the ASGs of those atoms, membership only adds or only removes allowed flows, so the states before and after the step suffice. [At the design target](../design/translation-engine.md#at-the-design-target) says how the engine runs the test at scale.
- The nightly integration test logs the interim states of membership swaps without failing, because the engine assumes them.
